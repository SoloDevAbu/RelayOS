# Workflow Engine

The Workflow Engine (`apps/workflow-service`) is the core execution heart of RelayOS. It acts as an asynchronous background worker that processes jobs dispatched by the [Ingestion Service](/docs/ingestion) and reliably executes workflow definitions step-by-step.

## Core Concepts

### Process Routing

The service is a single codebase but deploys in two modes using the `PROCESS_TYPE` environment variable:

- `PROCESS_TYPE=worker`: Subscribes to the BullMQ Redis queues, pulling pending executions and running them.
- `PROCESS_TYPE=api`: Exposes a Fastify web server for internal health checks (`/health`) and future administrative endpoints.

### State Machine

To guarantee atomic and safe execution, all database writes go through a rigid State Machine. The State Machine uses optimistic concurrency control at the PostgreSQL level. This ensures that even if multiple workers accidentally pick up the same execution ID, only one will successfully transition the state from `PENDING` to `RUNNING`.

**Legal step transitions:**

| From      | To          | When                                   |
| --------- | ----------- | -------------------------------------- |
| `PENDING` | `RUNNING`   | Step starts executing                  |
| `PENDING` | `SKIPPED`   | Step bypassed before it runs           |
| `RUNNING` | `COMPLETED` | Handler succeeded                      |
| `RUNNING` | `FAILED`    | Handler threw — first failure recorded |
| `RUNNING` | `WAITING_APPROVAL`| `APPROVAL` step paused execution |
| `FAILED`  | `RUNNING`   | New retry attempt beginning            |
| `FAILED`  | `SKIPPED`   | Retries exhausted, `onError: "SKIP"`   |
| `WAITING_APPROVAL`| `RUNNING` | Execution resumed after approval   |
| `WAITING_APPROVAL`| `CANCELLED`| Execution rejected via approval  |

### Context Manager

Workflows are dynamic; step 2 often depends on the output of step 1.
The **Context Manager** handles this by aggregating the output of every completed step into a single JSON object. To guarantee high performance, this context is **hot-cached in Redis** during the execution lifecycle. If a worker crashes and a job is retried, the context manager gracefully rebuilds the state from PostgreSQL and re-warms the Redis cache.

## Step Handlers

The engine walks the graph of your workflow definition and delegates logic to specialized handlers. Currently supported step types:

### `TOOL_CALL`

Makes an HTTP request to the external `tool-runtime` service. This is used for integrations, fetching data, or executing custom scripts. On failure, the retry policy determines whether to retry, skip, or fail (see [Retry & Failure Handling](#retry--failure-handling) below).

### `CONDITION`

Evaluates a logical operator (e.g., `eq`, `gt`, `in`, `exists`) or an expression string (e.g., `"{{payload.flag}} == true"`) against the current Execution Context. Depending on the result, it dynamically branches the workflow by overriding the `nextStepId`.

### `DELAY`

Pauses the workflow execution for a specified duration in milliseconds.

### `TRANSFORM`

Evaluates a `mapping` config object, resolving `{{payload.field}}` and `{{steps.stepId.field}}` templates against the current execution context. Produces a structured output object for downstream steps.

### `APPROVAL`

Pauses the workflow execution by transitioning the state to `WAITING_APPROVAL` and exiting the worker cleanly. A pending approval record is created in the database. The workflow resumes or is cancelled only when an external HTTP call approves or rejects the step.

### `AI_PLAN`

An autonomous agent loop powered by an LLM. Instead of executing a fixed action, the engine calls the [Agent Service](/docs/agent-service) in a `while(true)` loop, passing the goal, available tools, execution context, iteration history, and **recalled memories**. On each iteration the agent decides one action:

- **`tool_call`** → The engine calls the specified tool via the Tool Runtime. If the tool succeeds, the result is added to iteration history. If the tool fails (HTTP 500), the error is fed back to the agent as history so it can replan — tool errors do **not** terminate the step. After each successful tool call, a durable embed job is enqueued on the `memory:embed` queue to store the result for future recall.
- **`request_approval`** → The step pauses at `WAITING_APPROVAL`. After approval, the agent loop resumes with the full history intact.
- **`complete`** → The step finishes with the agent's summary. The full `iterationHistory` is persisted to `execution_steps.output`.

Before each call to the Agent Service, the engine calls `recall()` to retrieve the top-5 most semantically similar memory chunks scoped to:
- **Execution memory** (`scope = EXECUTION`) — tool results from the current execution.
- **Knowledge memory** (`scope = KNOWLEDGE`) — pre-seeded project-level context.

Recalled chunks are passed in the `memories` array on the planning request, giving the agent access to prior results and project knowledge without inflating the iteration history.

The loop is bounded by `maxIterations` (default 10). If exceeded, the step throws `AiPlanMaxIterationsError`.

## Retry & Failure Handling

When a step handler throws, the engine consults a **retry policy** before deciding what happens next. Each step can configure this via two fields on its definition:

| Field         | Type               | Default  | Description                                                                         |
| ------------- | ------------------ | -------- | ----------------------------------------------------------------------------------- |
| `maxAttempts` | `number`           | `1`      | Total attempts allowed (including the first). `maxAttempts: 3` = try up to 3 times. |
| `onError`     | `"FAIL" \| "SKIP"` | `"FAIL"` | What to do when all attempts are exhausted.                                         |

### Retry decisions

Given a failure on attempt _N_:

- **`N < maxAttempts`** → **retry**: A new delayed job is enqueued on the `workflow:retry` queue with an exponential backoff delay of `2^N × 1000ms` (attempt 1 → 2 s, attempt 2 → 4 s, attempt 3 → 8 s, …). The current job exits cleanly; the execution stays `RUNNING`.
- **`N ≥ maxAttempts`** → **dlq**: A `DlqJob` is enqueued on the `workflow:dlq` queue with the full failure payload. The `dlq-worker` picks it up and makes the final decision based on the `onError` config:
  - If `onError: "SKIP"`, the worker transitions the step to `SKIPPED` and resumes the execution from the next step.
  - If `onError: "FAIL"`, the worker transitions the execution to `FAILED`.

### Retry durability

Retries use **delayed BullMQ jobs**, not in-memory loops. This means:

- If the worker process crashes between attempts, the delayed job survives in Redis and is redelivered once the delay expires.
- Each attempt is recorded as a **separate row** in `execution_steps` (unique constraint on `(execution_id, step_id, attempt)`), giving a full audit trail.

### Example step definition

```json
{
  "id": "call-external-api",
  "type": "TOOL_CALL",
  "name": "Call External API",
  "config": { "toolId": "my-tool", "input": { "url": "{{payload.url}}" } },
  "maxAttempts": 3,
  "onError": "SKIP"
}
```

This step will be tried up to 3 times (with 2 s then 4 s delays). If it fails on the third attempt, it is skipped and the workflow continues.

## Worker Architecture

Three BullMQ Workers run inside the same `PROCESS_TYPE=worker` process, sharing a single Redis connection:

| Worker               | Queue              | Responsibility                                                                              |
| -------------------- | ------------------ | ------------------------------------------------------------------------------------------- |
| `execution-worker`   | `workflow:execute` | Picks up fresh executions and resumed executions, inserts step rows, runs all steps         |
| `retry-worker`       | `workflow:retry`   | Picks up delayed retry jobs, inserts a new step-attempt row, resumes from the failed step   |
| `memory-embed-worker`| `memory:embed`     | Picks up embed jobs enqueued by the AI_PLAN handler, calls the Gemini embeddings API, inserts `memory_chunks` rows |
| `dlq-worker`         | `workflow:dlq`     | Picks up dead-letter jobs after retries are exhausted and executes terminal `SKIP` or `FAIL` logic |

All three workers shut down gracefully together on `SIGTERM`/`SIGINT`.

## Tool Runtime

The `tool-runtime` service (`apps/tool-runtime`) is a minimal Fastify server on **port 8080** that the engine calls for `TOOL_CALL` steps.

### Endpoint

```
POST /internal/execute
```

**Body:**

```json
{ "toolId": "my-tool", "input": { ... }, "executionId": "exec-abc", "stepId": "step-1", "attempt": 1 }
```

**Response (200):**

```json
{ "output": { ... } }
```

Tools are registered via the Platform API and stored in the database. The Tool Runtime acts as a proxy, fetching tool credentials securely, validating input schemas, and executing the webhooks. A `flaky-test-tool` fixture is included for testing the retry path end-to-end — see the source for usage.

## Developing and Testing locally

```bash
# Run the API server (Port 3003)
npm run dev:api

# Run the background worker (execution + retry + dlq workers)
npm run dev:worker

# Run tool-runtime (Port 8080)
cd apps/tool-runtime && npm run dev
```

Run unit tests:

```bash
cd apps/workflow-service && pnpm test
```
